# py-schematron 2.1: descripción

## Análisis

py-schematron comprueba documentos TEI contra las reglas Schematron de su esquema, desde el terminal, e informa de cada infracción: cuántas veces se incumple cada regla y, para cada infracción, la línea y el `xml:id` del elemento identificable más cercano. Toma las reglas de un ODD, de un archivo ISO Schematron o de un esquema RelaxNG generado a partir de un ODD, que las lleva embebidas, y encuentra el esquema por sí solo en las instrucciones `<?xml-model?>` del documento. Su programa principal es py-schematron.py (hasta la versión 1.11 se llamó validate.py; en la 1.12, xmlvalidate.py, y de la 1.13 a la 1.21, cuando el proyecto se llamaba py-xmlvalidate, py-xmlvalidate.py); otro, py-schematron-all.sh, comprueba además la estructura con RelaxNG, y una extensión para Visual Studio Code y un paquete para Emacs muestran los mismos resultados en el editor, subrayados mientras se escribe. Lo hizo Nicolas Vaughan en 2026, para las ediciones del proyecto SMTrad.

Se apoya en cuatro piezas externas: Saxon, mediante saxonche (Saxon C), que evalúa las reglas con XPath 3.1; lxml, que encuentra las líneas y los `xml:id`s; jing, de James Clark, que comprueba la estructura RelaxNG; y la hoja de estilo `extract-isosch.xsl` de las TEI Stylesheets, que extrae el Schematron de un ODD. py-schematron es software libre, bajo la Licencia Pública General de GNU, versión 3 o posterior.

El proyecto partió de oXygen, con el que se validaban los documentos de SMTrad y que resultó fallar en silencio de tres maneras: muestra como mucho 100 avisos de validación y descarta el resto sin decirlo; cuando dos reglas de un pattern comparten contexto, solo se ejecuta la primera (*first-match shadowing*), y una regla vacía por error puede invalidar el esquema entero. Un documento podía parecer limpio sin estarlo. Al estudiar esos fallos quedaron claros los requisitos. Lo primero era que el informe estuviera siempre completo, o dijera exactamente cuántas infracciones quedaban sin listar, y diera un recuento total verificable; lo segundo, que las reglas se evaluaran igual que en oXygen, con XPath 3.1, respetando la semántica de ISO Schematron, y que un esquema sin reglas no aprobara nada en silencio.

Además, el programa tenía que servirle a cualquiera: desde el terminal, sobre muchos documentos a la vez, con los esquemas que de verdad usa el proyecto (un ODD propio y un RelaxNG publicado en GitHub), y sin tener que indicar el esquema cada vez. Más adelante se sumó otro requisito: ver los errores mientras se edita, en el editor, sin salir al terminal, con una instalación sencilla y sin tocar nunca los archivos del usuario.

## Diseño

py-schematron.py es un solo script, dividido en partes con un trabajo cada una. Las fuentes de reglas extraen el Schematron de un ODD o cosechan los patterns embebidos en un RelaxNG. La autodetección lee las instrucciones `<?xml-model?>`, descarga los esquemas remotos a un caché propio y clasifica cada esquema por su contenido. La lectura del esquema reúne patterns, reglas, asserts, reports y `let`s, y los mensajes con sus `<value-of>` y `<name/>`. La validación evalúa las reglas con Saxon y busca las líneas y los `xml:id`s con lxml. El informe sale en texto para el terminal o en JSON (`--json`) para otros programas.

py-schematron-all.sh valida en dos capas sobre el mismo RelaxNG: primero la estructura, con jing (o con lxml si jing no está), y luego las reglas, con py-schematron.py; combina los dos veredictos en su código de salida.

El primer fallo de oXygen desaparece por diseño: el recuento por regla está siempre completo, y `--max` limita solo el detalle, nunca el recuento, y dice cuántas infracciones quedaron sin listar. Los otros dos se vuelven visibles con ese recuento total. Una regla que no puede evaluarse se informa una sola vez y hace que el script salga con 3, porque el veredicto está incompleto; un esquema sin reglas termina con un error en lugar de aprobarlo todo. Del binding de oXygen viene también la decisión de evaluar con XPath 3.1, para que una regla dé el mismo resultado en los dos. Las reglas se ejecutan tal como están en el esquema, con sus mensajes y sus `role`, para que quien conozca el esquema reconozca cada infracción sin aprender nada nuevo; el informe nombra el pattern de cada una.

El informe JSON es la única fuente de los complementos. Los mensajes de progreso son también eventos del informe, con tipos estables en inglés; un error fatal da JSON con su mensaje, y cada infracción dice dónde está escrito su assert o report. Esa ubicación está en el archivo que se edita, el ODD o el RelaxNG, no en el `.sch` que se hace a partir de él: el programa busca allí la n-ésima regla con el mismo test, pues la extracción y la cosecha conservan el orden. Los dos complementos lo usan para saltar de un error a su regla. `--about` dice qué es el programa, quién lo hizo, su licencia y sus repositorios, y con qué corre (Python, saxonche, lxml, Saxon, el caché); los complementos tienen una orden *About* que muestra esa salida, de modo que un informe de error puede decir enseguida qué versiones intervinieron.

Para que el programa responda rápido, lo que se extrae, se cosecha o se descarga se guarda en un caché, que se rehace solo cuando cambia el esquema o el propio script.

Los archivos del proyecto son estos:

- `py-schematron.py`: el validador (940 líneas).
- `py-schematron-all.sh`: las dos capas, RelaxNG y Schematron (168 líneas).
- `py-schematron-install.py`: enlaza los dos scripts en `~/bin`, para llamarlos por su nombre desde cualquier carpeta.
- `installers/`: los instaladores para Linux, macOS y Windows.
- `tests/`: las pruebas (`test_py_schematron.py`).
- `tools/sync-plugins.py`: copia py-schematron.py en los clones de la extensión y del paquete de Emacs, o comprueba si sus copias son iguales.
- `tools/bundle-zip.py` y `tools/screenshots.py`: el zip de cada versión en `dist/` y las capturas de los README.
- `docs/`: las descripciones, las capturas y un ejemplo autónomo (`example/`): un texto TEI breve con errores deliberados y un esquema RelaxNG pequeño con reglas Schematron embebidas.

## Implementación

Está escrito en Python 3.15 o superior, con dos bibliotecas, saxonche y lxml, en unas 2700 líneas; la extensión, en unas 800 de TypeScript, y el paquete de Emacs, en unas 1550 de Emacs Lisp.

Antes se probaron implementaciones hechas. pyschematron tardaba minutos sobre el corpus, por las búsquedas `//*[@xml:id=…]` de las reglas; jing no admite `queryBinding="xslt2"`; SchXslt exigía administrar más archivos XSLT. Saxon, mediante saxonche, ya era una dependencia del proyecto, corre a la velocidad de C, y su XPath 3.1 es un superconjunto del de oXygen, de modo que `matches()`, `tokenize()`, `some`/`every` y `let` se comportan igual.

Los contextos relativos de las reglas se evalúan sobre todo el documento, y dentro de cada pattern cada nodo se compara solo con la primera regla cuyo contexto lo abarca, como prescribe ISO Schematron. Los `let` se traducen a `let $x := … return …` de XPath; los de schema y de pattern se evalúan con la raíz del documento como contexto, y `current()`, que es de XSLT, se liga al nodo de contexto. Los tests de una regla se evalúan juntos, con sus variables calculadas una sola vez por nodo, y cada regla se evalúa en una sola llamada a Saxon para todos sus nodos, porque Saxon compila cada expresión que recibe: antes, la regla de `<app>` se compilaba 2054 veces. Con este último cambio (versión 1.16), la edición latina, de unas 26 000 líneas, pasó de 11,5 a 1,9 segundos, con resultados idénticos en 39 documentos.

Todo lo que se guarda en el caché se escribe en un archivo temporal que luego se renombra, de modo que quien lo lea ve o ningún archivo o uno completo. Antes, dos validaciones simultáneas podían dejar en él una copia truncada del esquema, y todas las corridas siguientes fallaban. Una copia dañada se detecta y se reemplaza, y una descarga que no sea XML nunca se guarda.

### La extensión de VS Code

Tiene su propio repositorio, py-schematron-vscode. `extension.ts` se ocupa de la integración con el editor, y `parse.ts` lee los informes de py-schematron.py y de jing sin depender del editor, para poder probarlo aparte. La extensión ejecuta `py-schematron.py --json`, y jing si el esquema es RelaxNG, al abrir un documento, al guardarlo y cuando la escritura se detiene. Las infracciones aparecen subrayadas en el texto y en el panel Problemas, con la capa que encontró cada una (Schematron, RelaxNG o XML) y la gravedad de su `role`. El texto sin guardar se escribe en una carpeta temporal privada, nunca junto al archivo del usuario, y py-schematron.py lo trata con `--as` como si fuera el archivo real. Una barra de estado muestra el resultado del archivo actual, y la orden *Refresh Schema* vuelve a descargar un esquema remoto que haya cambiado.

### El paquete de Emacs

Tiene su propio repositorio, py-schematron.el. Se eligió un backend de Flymake, que viene con Emacs, y no un servidor de lenguaje: Python con sus bibliotecas arranca en unos 15 ms, y el tiempo de una edición grande se va en las reglas mismas. El backend trabaja como la extensión, con una copia temporal, `--json` y `--as`; el paquete registra también un comprobador de Flycheck, que se elige cuando Flycheck está instalado. Emacs 31 solo deja que Flymake corra sobre los archivos de `trusted-content`, y el paquete respeta esa regla también con Flycheck: el `<?xml-model?>` de un documento elige el esquema, y Saxon ejecuta su XPath, que puede leer archivos y pedir URL. Un archivo fuera de esa lista recibe un aviso con la línea que hay que añadir al archivo de inicio, y `M-x py-schematron-trust-file` confía en él después de preguntar. Después de cada comprobación, el paquete convierte el esquema RelaxNG a la sintaxis compacta con trang y se lo da a nxml-mode, que no sabe leer `<?xml-model?>`; nxml completa entonces los elementos y atributos que el esquema permite.

Cada complemento lleva su propia copia de py-schematron.py, y `tools/sync-plugins.py` copia en los dos cada versión nueva.

## Validación

py-schematron.py tiene 45 pruebas (`python3 -m unittest discover -s tests`), que lo ejecutan, junto con py-schematron-all.sh y el instalador, sobre documentos y esquemas pequeños hechos para cada caso, en una carpeta temporal: reglas y mensajes, *shadowing*, `let`s en cada nivel y `current()`, reglas rotas y códigos de salida, texto mal formado, las fuentes de las reglas (`-s`, `-r`, un ODD, `<?xml-model?>`, `--as`), el caché y una copia dañada en él, y un esquema remoto servido por un pequeño servidor web. Cada cambio se compara además antes y después sobre las ediciones y sobre el ejemplo de `docs/example/`. Las capturas de los README se rehacen con `tools/screenshots.py` y se revisan a ojo, y el zip de cada versión se prueba descomprimiéndolo y ejecutándolo. Una tarea del flujo de GitHub instala el programa de verdad en Linux, macOS y Windows y valida un documento con la orden instalada.

Las pruebas de los complementos están en sus repositorios. La extensión tiene 17 pruebas automáticas (`npm test`), que corren con el ejecutor de pruebas de Node. Comprueban cómo los informes de py-schematron.py y de jing se convierten en diagnósticos, las gravedades, dónde empiezan y terminan los subrayados y los mensajes de error; una de ellas ejecuta py-schematron.py de principio a fin. Otra prueba (`npm run test:integration`) ejecuta la extensión dentro de un VS Code real, sin pantalla y con un perfil propio: comprueba que los errores caigan en las líneas correctas y se vean subrayados, que se encuentre un elemento mal escrito, que se valide el texto sin guardar y que *Refresh Schema* recoja un esquema cambiado en un pequeño servidor web. Las pruebas de la extensión corren también en GitHub Actions con cada cambio.

El paquete de Emacs tiene 44 pruebas de ERT, que corren en un Emacs sin pantalla. Unas no necesitan Python: leen los informes de py-schematron.py y de jing, buscan el script y comprueban los arreglos de nxml en un Emacs nuevo. Las demás ejecutan los programas reales sobre documentos hechos para cada caso, mediante Flymake, Flycheck y trang: las líneas y los subrayados, el elemento mal escrito, el texto sin guardar, la comprobación cancelada por otra más nueva, el esquema remoto refrescado, el archivo fuera de `trusted-content`, que no quede ningún proceso ni copia temporal, y que nxml reciba el esquema y ofrezca sus elementos. El paquete se probó también instalándolo con `package-vc-install` y con Straight en perfiles vacíos, y sobre la edición latina: la comprobación de Flycheck tardó 2,6 segundos, nxml tuvo el esquema 0,7 segundos después y, dentro de un `<rdg>`, ofreció los 123 elementos que el esquema permite allí.

## Plataforma

py-schematron.py necesita Python 3.15 o superior, con saxonche y lxml; jing es opcional, para la capa estructural. La ruta del ODD (`-o`) necesita además `extract-isosch.xsl` y `common/functions.xsl` de las TEI Stylesheets, junto al script, o la carpeta de un clon completo de las TEI Stylesheets, que toma de `--stylesheets`, de `TEI_STYLESHEETS` o de la configuración de ODD2RNG, el script hermano que hace el RelaxNG a partir de un ODD; así ambos programas usan las mismas hojas de estilo. El paquete de Emacs necesita Emacs 31 o posterior. La extensión necesita Visual Studio Code 1.85 o posterior; en Linux conviene la versión nativa (RPM o deb) y no la Flatpak, que no ve el Python ni el jing del sistema.

Hasta la versión 2.1 el programa suponía una máquina con Linux y un python3 adecuado en el PATH. Desde entonces tiene instaladores para Linux, macOS y Windows, según el modelo de los de py-foliation: un script de shell y otro de PowerShell buscan Python 3.15 o posterior y ejecutan un install.py común, que descarga la última versión, crea un entorno de Python propio con saxonche y lxml, descarga las dos hojas de estilo de TEI y escribe las órdenes. Una vez instalado, solo necesita internet para descargar los esquemas remotos la primera vez, o al refrescarlos, y nunca escribe en los documentos que valida.

## Ambiente

Fue desarrollado en Fedora Linux 45 con KDE Plasma, con Python 3.15, Node.js 22, Visual Studio Code y Emacs 31, y con git. Las capturas se hacen con Xvfb, ImageMagick y Pillow.

El código está en tres repositorios publicados en GitHub y en Codeberg: py-schematron (https://codeberg.org/nivaca/py-schematron), py-schematron-vscode y py-schematron.el. Cada versión se etiqueta (`vX.Y` en el programa, `vA.B.C` en cada complemento) y se publica en las dos forjas: el programa, con el zip que hace `tools/bundle-zip.py`; la extensión, con su `.vsix`; el paquete de Emacs, con su zip. En el repositorio de la extensión, un flujo de trabajo de GitHub la prueba y empaqueta con cada etiqueta, y puede publicarla en el Visual Studio Marketplace con Trusted Publishing, sin guardar ninguna clave.

Para usar py-schematron.py basta ejecutar el instalador de cada sistema, o descomprimir el zip de una versión publicada, instalar saxonche y lxml (`pip install saxonche lxml`, mejor en un entorno virtual) y ejecutar `python3 py-schematron.py documento.xml`. La extensión se instala desde el Visual Studio Marketplace, o con el `.vsix` de una versión de py-schematron-vscode y `code --install-extension`; usa por sí sola el Python del instalador o, si no, el que indique el ajuste `schematron.pythonPath`. El paquete de Emacs se instala desde py-schematron.el con Straight o con `package-vc-install`, como explica su README. Las descargas de esquemas quedan en `.schema-cache/`, junto al script.
